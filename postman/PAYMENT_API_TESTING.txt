CHULBULPLAY - SABPAISA PAYMENT API TESTING (POSTMAN)
=====================================================

Base URL: http://localhost:5000

This project uses SabPaisa for payments. A real end-to-end success test needs
a valid SabPaisa test account and a successful checkout completed at the URL
returned by the initiate endpoint. Do not call the return or webhook endpoints
manually: they require a SabPaisa-generated signature.


PREREQUISITES
-------------
1. Configure the backend environment with all of these values:
   SABPAISA_API_KEY
   SABPAISA_SECRET_KEY
   SABPAISA_MERCHANT_ID
   SABPAISA_RETURN_URL
   Optional: SABPAISA_MODE=test

2. Enable SabPaisa in admin payment settings (step 1 below).

3. Create an active plan for the intended platform (app or website), then copy
   its `_id` to `{{planId}}`.

4. Log in as a normal user and save the returned JWT as `{{userToken}}`.
   The payment request needs a valid email and an Indian 10-digit mobile number
   beginning with 6, 7, 8, or 9. The user must not already hold an active
   subscription for that platform.


ADMIN SETUP
===========

1. VIEW PAYMENT SETTINGS
------------------------
GET {{baseUrl}}/api/admin/payment-settings
Authorization: Bearer {{adminToken}}
Body: none


2. ENABLE SABPAISA
------------------
PUT {{baseUrl}}/api/admin/payment-settings
Authorization: Bearer {{adminToken}}
Content-Type: application/json

Body:
{
  "sabpaisaEnabled": true,
  "sabpaisaMode": "test"
}

`sabpaisaEnabled` must be true. The gateway still reports disabled unless the
four required SABPAISA environment variables are also configured on the server.


USER PAYMENT FLOW
=================

3. CONFIRM ACTIVE GATEWAY
-------------------------
GET {{baseUrl}}/api/payment/gateways
Body: none

Expected result:
{
  "success": true,
  "gateways": {
    "sabpaisa": {
      "enabled": true,
      "name": "SabPaisa",
      "mode": "test"
    }
  },
  "defaultGateway": "sabpaisa"
}

If `enabled` is false, do not continue until admin settings and server
environment variables are configured.


4. LIST AVAILABLE PLANS
-----------------------
GET {{baseUrl}}/api/plan?platform=app
Body: none

For website plans:
GET {{baseUrl}}/api/plan?platform=website

Copy an active plan `_id` to `{{planId}}`.


5. OPTIONAL: VALIDATE PROMO CODE
--------------------------------
POST {{baseUrl}}/api/promo/apply
Authorization: Bearer {{userToken}}
Content-Type: application/json

Body:
{
  "code": "WELCOME10",
  "planId": "{{planId}}"
}

Use a valid code returned or created in your environment. This checks the code;
the actual payment request applies it via `promoCode`.


6. INITIATE SABPAISA PAYMENT
----------------------------
POST {{baseUrl}}/api/payment/sabpaisa/initiate
Authorization: Bearer {{userToken}}
Content-Type: application/json

Body:
{
  "planId": "{{planId}}",
  "platform": "app",
  "promoCode": "WELCOME10",
  "name": "Test User",
  "email": "test@example.com",
  "phone": "9876543210"
}

`promoCode` is optional; omit it when not testing a promotion. `platform` may
be `app` or `website`. For website requests it is also valid to send:
X-Platform: website

Successful response fields:
{
  "success": true,
  "orderId": "SP_<generated value>",
  "finalAmount": 89.1,
  "platform": "app",
  "checkoutUrl": "https://..."
}

Copy `orderId` into `{{orderId}}`. Open `checkoutUrl` in a browser and finish
the payment with SabPaisa's test credentials/test payment method.


7. CHECK PAYMENT STATUS
-----------------------
GET {{baseUrl}}/api/payment/sabpaisa/status/{{orderId}}
Authorization: Bearer {{userToken}}
Body: none

Possible response while payment is pending:
{
  "success": true,
  "status": "pending"
}

After SabPaisa records a successful payment, this endpoint reconciles the
order, creates the subscription, and returns `status: "active"` with the
subscription object.


8. CHECK USER SUBSCRIPTION
--------------------------
GET {{baseUrl}}/api/subscription/status?platform=app
Authorization: Bearer {{userToken}}
Body: none

For a website subscription:
GET {{baseUrl}}/api/subscription/status?platform=website

The successful response includes `subscription` and `remainingDays`.


COMPATIBILITY ENDPOINTS
=======================

9. CREATE ORDER (LEGACY ALIAS)
------------------------------
POST {{baseUrl}}/api/payment/create-order
Authorization: Bearer {{userToken}}
Content-Type: application/json

Body: use exactly the same body as step 6.

This calls the same SabPaisa initiation logic as `/sabpaisa/initiate`.


10. INITIATE (LEGACY ALIAS)
---------------------------
POST {{baseUrl}}/api/payment/initiate
Authorization: Bearer {{userToken}}
Content-Type: application/json

Body: use exactly the same body as step 6.


11. VERIFY PAYMENT (LEGACY STATUS CHECK)
-----------------------------------------
POST {{baseUrl}}/api/payment/verify
Authorization: Bearer {{userToken}}
Content-Type: application/json

Body:
{
  "orderId": "{{orderId}}"
}

This is an alias for the SabPaisa status check when `orderId` is supplied.


SUBSCRIPTION TEST ENDPOINTS
===========================

12. CANCEL A SUBSCRIPTION
-------------------------
DELETE {{baseUrl}}/api/subscription/cancel
Authorization: Bearer {{userToken}}
Content-Type: application/json

Body:
{
  "subscriptionId": "{{subscriptionId}}"
}

Copy `subscriptionId` from the result of step 7 or step 8. Although this is a
DELETE request, this API requires the JSON request body.

The alias below performs the same action:
DELETE {{baseUrl}}/api/subscription/status


SANDBOX CALLBACK ENDPOINTS — DO NOT MANUALLY TEST
==================================================

GET  {{baseUrl}}/api/payment/sabpaisa/return
POST {{baseUrl}}/api/payment/sabpaisa/return
POST {{baseUrl}}/api/payment/sabpaisa/webhook

SabPaisa calls these endpoints after checkout. The return route requires a
valid signed query string; the webhook requires the `X-SabPaisa-Signature`
header calculated over its raw body. Manual Postman calls will correctly fail
with an invalid-signature response and cannot simulate a paid transaction.


COMMON ERRORS
=============

403 "SabPaisa is disabled by the administrator"
  Enable `sabpaisaEnabled` in admin payment settings.

503 "credentials or return URL are not configured"
  Add the required SABPAISA environment variables and restart/redeploy backend.

400 "A valid email address is required"
  Send a valid `email` in step 6 or save one on the user profile.

400 "A valid 10-digit Indian mobile number..."
  Send `phone` without country code, for example `9876543210`.

400 "already have an active ... subscription"
  Cancel or expire the existing subscription first, or test with another user.
